A practical starting point

Three ways to
test the MCP.

Check the contract, exercise the real clients, then add a small model check. All three use a synthetic backend, so you do not need a MidBrain deployment or Docker.

01 / ZERO MODEL CALLS

Dry-smoke

Does the MCP behave correctly?

The harness directly checks all 12 tools, their schemas, configuration, credential handling and failure cases. Native connection or discovery is checked separately for each client.

Harness → installed MCP → fixture API
Separate check → native client discovery

Start here after changing tools, installation or configuration.

$0 model inference · multiple clients per run

02 / ZERO MODEL CALLS

Scripted-smoke

Can the real client execute our tools?

A local provider simulator sends predetermined tool calls to the real client. It executes all 12 MCP tools, then a 503 failure and recovery. Native events, MCP traces and backend receipts must agree.

Local script → real client → MCP → API
Result → MCP → client → local script

Use next to catch client dispatch and result-delivery problems.

$0 model inference · one client per run

03 / PAID MODEL CALLS

Live-smoke

Can a real model complete the tool loop?

Two fresh sessions per client check an explicitly requested search and result consumption, then an error and recovery. It uses the real client and model against the same kind of synthetic API.

Real model → real client → MCP → API
Result → client → model → verified answer

Use for a small final check of the model boundary.

Usage-based cost · plan first, execute explicitly

The shared boundary: these modes test MCP integration, not production memory quality. Scripted decisions do not prove model judgment; live-smoke tests requested tool use, not spontaneous tool selection.

From checkout to first report

All five clients are supported: Claude Code, Codex, Pi, OpenCode and Hermes. The harness launches them for you in an isolated test home.

1

Prepare the repository

From your checkout, select the testing branch and install dependencies. You need Node 20+, npm and Git. Claude and Codex must already be on PATH. Hermes installation requires uv.

git switch mcp-testing-layers
npm ci
2

Check the MCP without models

Run Claude and Codex first, or omit --clients to check all five. Neither dry-smoke nor scripted-smoke loads provider credentials or needs API keys.

node harness/run.mjs dry-smoke --clients claude,codex

# All five; install missing Pi, OpenCode and Hermes locally:
node harness/run.mjs dry-smoke --install-clients
3

Exercise native tool dispatch without models

Choose one client per command. Each run has a 90-second native deadline. Claude, Codex, Pi and Hermes run 14 MCP calls; OpenCode adds a fifteenth call to a second MCP server to test same-name tool routing.

node harness/run.mjs scripted-smoke --clients claude
node harness/run.mjs scripted-smoke --clients codex

# Example with a run-local client installation:
node harness/run.mjs scripted-smoke --clients pi --install-clients
4

Plan the small paid check

The example uses GPT-6 Luna for Codex/OpenCode and Haiku for Claude Code/Hermes/Pi. Claude uses its native Anthropic path; it does not run Luna through a bridge. This command only prints a plan.

node harness/run.mjs live-smoke \
  --config harness/live-smoke.example.json \
  --clients claude,codex

To execute, provide ANTHROPIC_API_KEY and OPENAI_API_KEY in your environment or private harness/.env, then add --execute. The pair runs four native sessions and can incur charges.

node harness/run.mjs live-smoke \
  --config harness/live-smoke.example.json \
  --clients claude,codex \
  --execute

Two sessions per client can involve several provider requests. A failed first scenario skips that client’s second paid scenario.

The arguments you need

ArgumentAvailable inWhat it does
--clientsAll threeclaude,codex for dry/live; exactly one name for scripted. Dry defaults to all five, scripted to Pi, live to clients in the JSON config.
--install-clientsAll threeInstalls missing Pi/OpenCode/Hermes inside the run directory. Claude/Codex must be preinstalled. Downloads can use the network.
--root DIRAll threeChanges the output location. Default: ~/.midbrain-harness, unless MIDBRAIN_HARNESS_ROOT is set.
--config FILELive onlyRequired JSON file with explicit models; optionally set timeoutMs and maxMcpCalls.
--executeLive onlyStarts real model sessions. Without it, the command only prints a plan. --plan explicitly selects that default.

Live defaults: 90,000 ms and four MCP calls per session. Edit these in the JSON, not as CLI flags. Allowed ranges: 10,000–180,000 ms and 2–8 MCP calls. Time and tool-call limits do not impose a dollar cap. Dry/scripted reject model and live-provider flags.

Read the report, inspect the evidence

Every executed run prints its report.html path. Open it directly in your browser. Outputs normally live under ~/.midbrain-harness/runs/<run-id>/.

What you receive

  • HTML: readable outcomes and inspectable tool exchanges.
  • Markdown and JSON: a written summary and structured evidence.
  • JUnit: CI-friendly results.
  • Identity and isolation receipts: candidate hashes, client versions, host and watched-file checks.

What the logs mean

  • Dry: MCP context preview—definitions, arguments and results from direct probes.
  • Scripted: actual requests sent by the client to the local provider simulator, with synthetic credentials redacted.
  • Live: native tool events, MCP exchanges and backend receipts, plus available usage. Full provider request logging is not guaranteed.
PASS · checks agreeFAIL · assertion failedBLOCKED · prerequisite missingINCOMPLETE · run did not finish

Failed, blocked and incomplete runs exit nonzero. Missing tools are not silently treated as passes. Ctrl+C stops owned processes and retains available evidence; a hard kill can leave only partial logs. A final answer claiming success cannot substitute for tool receipts.

What is validated today?

Recorded Linux/macOS CI passed all 12 native jobs for commit 6c29a38: dry-smoke across five clients and scripted-smoke for each client on both hosts. That evidence contains 1,026 passing assertions.

Native Windows runs and paid live-smoke remain unvalidated. These checks do not establish memory ranking, production service reliability, capture correctness or every possible third-party conflict. Test homes are isolated and watched host files are checked; this is not an OS network sandbox.

Suggested order: dry-smoke → scripted-smoke → an explicitly executed, small live-smoke run.
